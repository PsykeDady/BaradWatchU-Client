# Client BaradWatchU

*Nove di questi furono dati ai Dev, che i tristi bug attendono; sette ai SysAdmin, nelle loro sale di server; tre ai Security Officer, custodi delle policy segrete.*

[Read in English](README.md)

BaradWatchU Client controlla la postazione su cui viene eseguito. Audit, impostazioni e storico restano locali; il Server non è necessario. I target di sviluppo sono Arch Linux e, dal 2026-11-08, Windows 11 (in sviluppo, vedi [Windows](#windows-in-sviluppo)); macOS non è supportato.

## Controlli: una cartella ciascuno

Ogni controllo, integrato o personalizzato, è una cartella con il nome del suo ID che contiene `configuration.json` e il tool da eseguire:

```text
custom-checks/
└── CUSTOM-001/
    ├── configuration.json
    └── CUSTOM-001.sh
```

```json
{
  "schemaVersion": "baradwatchu.custom-checks.v1",
  "id": "CUSTOM-001",
  "name": "Password Reminder",
  "description": "Che cosa verifica il controllo",
  "priority": "OPTIONAL",
  "enabled": true,
  "toolPath": "./CUSTOM-001.sh",
  "arguments": [],
  "expectedSha256": "<sha256 del tool>",
  "version": 1,
  "timeoutSeconds": 20,
  "parameters": {},
  "overrideBuiltinId": null
}
```

- I controlli integrati stanno in `share/baradwatchu-client/catalog/checks/REQ-*/` dell'installazione (Windows: `catalog/checks-windows/REQ-*/`); quelli personalizzati in `$XDG_CONFIG_HOME/baradwatchu/custom-checks/CUSTOM-*/` (predefinito `~/.config/baradwatchu/custom-checks/`; Windows `%APPDATA%\baradwatchu\custom-checks\`). Una cartella `custom-tools` della versione precedente viene rinominata in `custom-checks` al primo utilizzo, senza modificarne il contenuto.
- `id` deve coincidere con il nome della cartella e iniziare con `CUSTOM-` (lettere maiuscole, cifre, trattini). `toolPath` è relativo alla cartella. `arguments` viene passato direttamente al tool, senza shell. `timeoutSeconds` (1–300, predefinito 20) e `version` sono facoltativi. `parameters` è un oggetto JSON inviato al tool su stdin come `{"requirementId":…,"parameters":{…}}`. I campi sconosciuti sono rifiutati. Le priorità sono `HIGHEST`, `HIGH`, `MEDIUM`, `LOW` e `OPTIONAL` e non cambiano l'esito.
- Un controllo personalizzato stampa su stdout **un solo** oggetto JSON ed esce con codice 0: `{"status":"PASS","summary":"Esito leggibile","details":["prova"]}`. Gli stati sono `PASS`, `FAIL`, `WARNING` (mostrato come `WARN`) ed `ERROR`; `details` è facoltativo, stringa o array. Non ripete il proprio ID. I tool integrati restituiscono anche il loro `id`.
- Il tool viene avviato nella propria cartella con l'utente corrente, senza shell né elevazione di privilegi, con un ambiente pulito (`PATH` è `/usr/bin:/bin`, più `~/.local/bin` per i controlli personalizzati), un proprio process group e un output limitato. Al timeout viene terminato l'intero process group, compresi gli helper avviati dallo script. Codice di uscita diverso da zero, JSON non valido o timeout danno `ERROR`, e lo stderr del tool compare nei dettagli. Per come vengono avviati i tool su Windows vedi [Windows](#windows-in-sviluppo).
- **Integrità:** prima di ogni esecuzione lo SHA-256 del tool viene confrontato con `expectedSha256` (per gli integrati: il manifest incorporato nell'agente). Se non coincide il tool **non viene eseguito** e l'esito è `ERROR`. Dopo una modifica voluta, registra il nuovo file con `baradwatchu-agent custom accept CUSTOM-ID` oppure con **Accetta versione attuale** nella dashboard; caricare un nuovo file dalla dashboard fa lo stesso e incrementa `version`. Un controllo scritto a mano senza `expectedSha256` resta bloccato finché non viene accettato. Per i controlli personalizzati l'hash copre solo il file di ingresso; i controlli integrati sono verificati file per file (vedi [Provider e integrità dell'installazione](#provider-e-integrità-dellinstallazione)).
- **Isolamento dei guasti:** una cartella personalizzata con configurazione non valida non blocca gli altri controlli. Compare come controllo in `ERROR` con il motivo esatto (per esempio un campo sconosciuto) e si può eliminare da CLI o dashboard. Le cartelle il cui nome non è un ID `CUSTOM-` valido vengono segnalate come ignorate da `refresh` e dalla dashboard.
- **Le modifiche locali sono sempre controlli personalizzati.** Abilitazione, priorità e parametri di un controllo integrato si cambiano solo con una cartella CUSTOM che lo sostituisce, così ogni modifica locale è visibile («Configurazione modificata da CUSTOM-…» nella dashboard, `isOverride`/`configurationOverride` nei report). `enable|disable`, `priority`, `configure` e i comandi della dashboard scrivono un **override di sola configurazione** `CUSTOM-<ID>/configuration.json` (`overrideBuiltinId`, senza `toolPath`, `expectedSha256` né `arguments`): girano comunque i file ufficiali, verificati dal manifest, con `enabled`, `priority` e `parameters` della cartella. Tornando ai valori ufficiali, oppure con **Ripristina** nella dashboard, la cartella viene eliminata. Su un controllo personalizzato gli stessi comandi modificano il suo `configuration.json`. Un override con script (`toolPath`) sostituisce l'integrato per intero. Il vecchio `settings.json` non viene più letto; se presente, `refresh` e la dashboard lo segnalano come file ignorato che si può eliminare.

Le cartelle vengono riscansionate a ogni `list`, audit e richiesta della dashboard; `baradwatchu-agent refresh` o **Riscansiona cartelle** nella dashboard forzano la scansione e segnalano le cartelle non valide.

## Provider e integrità dell'installazione

**Provider.** Un requisito integrato può avere più implementazioni intercambiabili (provider), uno script per prodotto in `providers/` nella cartella del controllo, dichiarate in `configuration.json` sotto `providers` (`name`, `toolPath`, `parameters`, `timeoutSeconds` facoltativo) al posto di `toolPath`. Oggi li usa solo REQ-002 (antivirus): `clamav` e `bitdefender-gravityzone` su Linux, `defender`, `bitdefender-gravityzone` e `security-center` su Windows. A ogni audit girano tutti i provider e ciascuno ha il proprio esito (JSON `extensions.providers`, dashboard, PDF). Il parametro del requisito `acceptedProviders` decide l'esito:

- vuoto (predefinito per tutti gli integrati): basta un provider `PASS`; se non c'è, l'esito è `ERROR` se un provider non è riuscito a girare, altrimenti `WARN` se uno è inconcludente, altrimenti `FAIL`;
- non vuoto, es. `["bitdefender-gravityzone"]`: ogni provider elencato è obbligatorio e deve dare `PASS`; decide il peggiore (`ERROR` > `FAIL` > `WARN`). I provider non elencati girano comunque e sono mostrati come facoltativi;
- un ID sconosciuto o un valore che non è un elenco dà `ERROR` e nessun provider viene eseguito.

`providerParameters` sovrascrive i valori predefiniti di un provider, es. `{"acceptedProviders":["bitdefender-gravityzone"],"providerParameters":{"bitdefender-gravityzone":{"maxSignatureAgeDays":1}}}`. Si impostano dalla dashboard (parametri di REQ-002) o con `baradwatchu-agent configure REQ-002 '…'`: entrambi creano l'override di sola configurazione `CUSTOM-REQ-002`. I controlli personalizzati non possono dichiarare provider; un controllo personalizzato che sostituisce REQ-002 lo sostituisce per intero.

Il provider Bitdefender GravityZone è scritto dalla documentazione pubblica Bitdefender e **non è verificato su un endpoint gestito**. Linux: cartella `/opt/bitdefender-security-tools`, unità systemd `bdsec*` (la principale `bdsec.service` attiva e abilitata), `bduitool get ps` per stato on-access e ultimo aggiornamento (richiede root, quindi un audit senza privilegi segnala quello stato come non verificabile: al massimo `WARN`, mai `PASS`). Windows: voce di disinstallazione di Bitdefender Endpoint Security Tools o `product.console.exe`, servizi il cui nome contiene "Bitdefender", stato nel Centro sicurezza di Windows, `product.console.exe /c GetUpdateStatus antivirus`. Parametri: `maxSignatureAgeDays` (3), `expectedCompanyId` (vuoto: non controllato; se impostato viene segnalato come non verificabile finché non si conferma una fonte affidabile).

**Integrità dell'installazione.** `catalog/builtin-tools.sha256` elenca lo SHA-256 di **ogni file** di ogni cartella dei controlli integrati (script, provider, script di supporto, `configuration.json`), una riga per file, per Linux e Windows. È incorporato nell'agente in fase di build: modificare la copia installata non cambia nulla. A ogni audit l'agente calcola l'hash dei file integrati installati, riporta ciascun file nel JSON (`installation`: stato `VERIFIED`, `MODIFIED`, `MISSING`, `UNEXPECTED` o `UNSAFE`, hash atteso ed effettivo, più l'hash del manifest) e mostra una riga di riepilogo in CLI, dashboard e PDF. Un controllo integrato la cui cartella differisce dal manifest dà `ERROR` e **non viene eseguito**; una cartella integrata cancellata compare come controllo in `ERROR`. Ogni differenza genera un evento `INTEGRITY_ISSUE`. I controlli personalizzati non sono nel manifest e mantengono il proprio hash sul file di ingresso. Gli hash per file servono al futuro controllo dell'installazione da parte del Server (non ancora implementato); un binario dell'agente modificato può comunque mentire su di essi. Dopo aver modificato un controllo integrato esegui `scripts/update-builtin-hashes.sh`: aggiorna `expectedSha256` dei controlli con file di ingresso e riscrive il manifest.

## Controlli integrati (Arch Linux)

I criteri seguono la baseline delle postazioni in `REQUIREMENTS.md` §5. Le soglie sono parametri nei rispettivi `configuration.json` e si cambiano con `configure` o dalla dashboard, che creano un override di configurazione `CUSTOM-<ID>` visibile. Se le prove mancano o non sono leggibili l'esito è `WARN`, mai `PASS`; ciò che risulta spento è `FAIL`.

| ID | PASS quando |
|---|---|
| REQ-001 | `checkupdates` (pacman-contrib) non trova aggiornamenti nei repository ufficiali (AUR escluso). Viene riportata la data dell'ultimo full upgrade da `pacman.log`. Contatta i mirror Arch; timeout 90 s. |
| REQ-002 | Basato su provider (vedi [Provider](#provider-e-integrità-dellinstallazione)). `clamav`: daemon ClamAV, freshclam e clamonacc attivi, `OnAccessPrevention yes` con almeno un percorso sorvegliato, firme giornaliere vecchie al massimo 3 giorni. `bitdefender-gravityzone`: vedi sopra. |
| REQ-003 | UFW, firewalld o nftables mostrano un filtraggio operativo verificato. Tutti i firewall gestiti esplicitamente inattivi danno `FAIL`; regole non leggibili altrimenti `WARN`. |
| REQ-004 | Almeno un metodo di filtro DNS è completo: dnsmasq attivo **e** abilitato all'avvio con almeno `minimumDnsmasqRules` (1000) regole di blocco, oppure una blocklist [HaGeZi](https://github.com/hagezi/dns-blocklists-legacy) in `/etc/hosts` (vedi [Liste hosts HaGeZi](#liste-hosts-hagezi)). Un `resolv.conf` che non punta a loopback (per esempio con una VPN connessa) viene riportato come osservazione. |
| REQ-005 | Cato o WireGuard connessi. Installato ma disconnesso dà `WARN`; nessuno dei due installato dà `FAIL`. |
| REQ-006 | Almeno un metodo di cifratura attivo: dispositivo LUKS/dm-crypt, eCryptfs montato (i dettagli indicano se copre la home) o container CryFS montato. Non certifica tutte le aree dati. |
| REQ-007 | KDE Plasma 6 Wayland: `Autolock=true`, `Timeout` ≤ `maxTimeoutMinutes` (5), `LockGrace` ≤ `maxLockGraceSeconds` (0, password richiesta subito), blocco alla ripresa attivo. Le altre sessioni sono `NOT_APPLICABLE`. |
| REQ-008 | Età massima della password dell'account ≤ `maxPasswordAgeDays` (60) e non "never"; preavviso ≥ `minimumWarningDays` (10); `PASS_MAX_DAYS` in `/etc/login.defs` entro lo stesso limite; pwquality `minlen` ≥ 14, `minclass` ≥ 4, `ucredit`/`lcredit`/`dcredit`/`ocredit` = -1 (`requireCharacterCredits`), con `pam_pwquality` o `pam_passwdqc` in PAM. |
| REQ-009 | Il firmware riporta Secure Boot attivo e SetupMode disattivato; l'output di `systemd-analyze has-tpm2` viene registrato. |

### Liste hosts HaGeZi

Il metodo del file hosts di REQ-004 (Linux e Windows) accetta solo una lista HaGeZi: un'intestazione che inizia con `# Title: HaGeZi's` e il cui `# Homepage:` è sotto `github.com/hagezi/`. HaGeZi ora pubblica il formato hosts nel [repository legacy](https://github.com/hagezi/dns-blocklists-legacy) (`hosts/*.txt`, anche nelle varianti `*-compressed.txt` con fino a 9 nomi per riga). Si possono concatenare più liste. Il file deve contenere almeno tante righe di blocco (`0.0.0.0` o `::`) quante ne dichiarano le intestazioni in `# Number of entries` (altrimenti la lista è troncata: `FAIL`) e almeno `minimumHostsEntries` (10000) nomi bloccati. Una lista il cui `# Last modified` è più vecchio di `maxListAgeDays` (30, `0` disattiva la verifica) dà `WARN`. Con `requireHagezi: false` è accettata qualsiasi blocklist di dimensione sufficiente. I nomi host non vengono mai riportati. Il controllo funziona offline: non scarica la lista per confrontarne il contenuto.

## Windows (in sviluppo)

I controlli integrati sono script PowerShell in `catalog/checks-windows/REQ-*/check.ps1` (REQ-002: `providers/*.ps1`), elencati con i loro hash nello stesso `catalog/builtin-tools.sha256` (colonna piattaforma `windows`). Girano con l'utente corrente **senza diritti di amministratore**, quindi usano fonti leggibili da un utente standard (CIM/COM, registro, API Win32 documentate) e, dove possibile, non l'output localizzato dei comandi.

| ID | PASS quando (Windows) |
|---|---|
| REQ-001 | Windows Update (ricerca COM, senza elevazione) non trova aggiornamenti software non installati e non nascosti. Aggiornamenti in sospeso danno `FAIL` con il numero di quelli di sicurezza; una ricerca che non riesce a completarsi dà `WARN`. Può contattare Windows Update; timeout 240 s. |
| REQ-002 | Basato su provider. `defender`: Microsoft Defender è il motore attivo con protezione in tempo reale attiva (altrimenti `FAIL`) e firme vecchie al massimo `maxSignatureAgeDays` (7) giorni (altrimenti `WARN`). `security-center`: un qualsiasi antivirus registrato nel Centro sicurezza di Windows è attivo con firme aggiornate; nessuno registrato o tutti disattivati dà `FAIL`. `bitdefender-gravityzone`: vedi [Provider](#provider-e-integrità-dellinstallazione). Gli script dei provider non sono ancora stati eseguiti su Windows. |
| REQ-003 | Windows Defender Firewall è attivo con traffico in ingresso `Block` su ogni profilo, letto dall'`ActiveStore` effettivo (locale e Criteri di gruppo), oppure è attivo un firewall di terze parti registrato nel Centro sicurezza. |
| REQ-004 | Una lista HaGeZi completa e recente nel file hosts di sistema (vedi sopra). Resolver configurati e criterio `DnsOverHttpsMode` di Chrome/Edge sono riportati come osservazioni. |
| REQ-005 | Cato Client è installato e firmato da Cato Networks, `CatoClientCliAT.exe antitamper status` risponde e una scheda di rete Cato è `Up`. Presente ma non connesso, o che non risponde, dà `WARN`; non installato dà `FAIL`. Quale delle due schede Cato porta il tunnel non è ancora stato verificato su un dispositivo connesso. |
| REQ-006 | BitLocker protegge l'unità di sistema, letto dalla proprietà di Esplora file `System.Volume.BitLockerProtection` (la classe WMI di BitLocker e `manage-bde` richiedono diritti di amministratore). Disattivato, in decifratura o sospeso dà `FAIL`; cifratura in corso, o altre unità fisse non protette o non determinabili, dà `WARN`. |
| REQ-007 | Almeno un metodo blocca la sessione entro `maxTimeoutMinutes` (5): il criterio di limite di inattività del computer, un salvaschermo protetto da password (prevalgono i valori dei criteri) oppure la sospensione con accesso richiesto alla riattivazione per ogni fonte di alimentazione del dispositivo. Un `ScreenSaverGracePeriod` superiore a `maxLockGraceSeconds` (0) rende insufficiente il metodo del salvaschermo. |
| REQ-008 | Criterio password locale letto tramite l'API SAM accessibile agli utenti standard (i dati per cui `secedit` richiede elevazione): età massima impostata e ≤ `maxPasswordAgeDays` (60), lunghezza minima ≥ `minimumLength` (14), complessità attiva (`requireComplexity`; Windows richiede 3 categorie di caratteri su 4), preavviso di scadenza ≥ `minimumWarningDays` (10, predefinito di Windows 5) e nessun account locale attivo con password che non scade mai. Account Microsoft e appartenenza a un dominio danno `WARN` perché li governa un'altra autorità. I nomi degli account non vengono mai riportati. Il PIN di Windows Hello non viene verificato. |
| REQ-009 | Firmware UEFI con Secure Boot attivo (stato registrato da Windows all'avvio) e un TPM 2.0 (TPM Base Services). BIOS legacy, Secure Boot disattivato o assenza di TPM 2.0 danno `FAIL`. |

Come vengono avviati i tool su Windows: gli script `.ps1` tramite Windows PowerShell 5.1 (`%SystemRoot%\System32\WindowsPowerShell\v1.0\powershell.exe -NoLogo -NoProfile -NonInteractive -ExecutionPolicy Bypass -File`, con percorso assoluto), i file `.exe` direttamente; gli altri tipi di file danno `ERROR`. Il bypass della execution policy vale solo per quel processo: a decidere che cosa gira è il controllo SHA-256. L'ambiente viene ripulito (`PATH` = System32, Windows, WBEM e la cartella di PowerShell, più le cartelle standard dell'utente), non compare alcuna finestra di console, e il tool con tutti i processi che avvia appartiene a un Job Object che viene terminato al timeout e dopo l'uscita del tool. Gli script che stampano testo non ASCII vanno salvati in UTF-8 con BOM (Windows PowerShell 5.1 legge i file senza BOM nella code page ANSI); quelli integrati lo sono, e `.gitattributes` li mantiene in CRLF così il loro hash è identico a ogni checkout.

Cartelle dati su Windows (quando le variabili XDG non sono impostate): impostazioni e controlli personalizzati `%APPDATA%\baradwatchu\`, eventi e richieste di consenso `%LOCALAPPDATA%\baradwatchu\state\` (file di runtime in `state\run\`), storico degli audit `%LOCALAPPDATA%\baradwatchu\cache\audit\`. Il file di avvio della dashboard viene aperto con Esplora file, che usa il browser predefinito.

## CLI

```sh
baradwatchu-agent list [--json]
baradwatchu-agent refresh
baradwatchu-agent enable|disable ID
baradwatchu-agent priority ID HIGHEST|HIGH|MEDIUM|LOW|OPTIONAL
baradwatchu-agent configure REQ-007 '{"maxTimeoutMinutes":5,"maxLockGraceSeconds":0}'
baradwatchu-agent check ID [--log]
baradwatchu-agent audit [--json] [--notify] [--log]
baradwatchu-agent status [--json]
baradwatchu-agent history [--json]
baradwatchu-agent history delete STAMP
baradwatchu-agent history clear --yes
baradwatchu-agent custom accept CUSTOM-ID
baradwatchu-agent custom remove CUSTOM-ID
baradwatchu-agent dashboard [--no-browser] [--open status|custom|history|notifications|settings]
baradwatchu-agent notifications [--json]
baradwatchu-agent notifications set enabled|informative on|off
baradwatchu-agent events --json [--after ID]
baradwatchu-agent consent simulate [--server ID] [--account NAME] [--account-id ID] [--device NAME] [--ttl SECONDS]
baradwatchu-agent consent list [--json]
baradwatchu-agent consent accept|reject REQUEST-ID
baradwatchu-agent identity generate [--yes] | identity reset [--yes]
baradwatchu-agent identity show [--json] | identity export [--output FILE]
baradwatchu-agent trust list [--json] | trust show SERVER-ID [--json]
baradwatchu-agent trust import FILE [--fingerprint SHA256:…]
baradwatchu-agent trust revoke SERVER-ID [--yes] | trust clear [--yes]
baradwatchu-agent remote enable | remote disable | remote status [--json]
baradwatchu-agent service run          # servizio di sistema (systemd, launchd, Windows Service)
baradwatchu-tray [--version | --help | autostart enable|disable|status [--json]]
```

In sviluppo usa `cargo run -p baradwatchu-agent -- …`. Codici di uscita di `audit`/`check`: 0 tutto conforme (o disabilitato/non applicabile), 4 almeno un `WARN`, 3 almeno un `FAIL`, 1 almeno un `ERROR`, 2 errore d'uso. Su Linux ogni audit salva sempre il report JSON in `~/.cache/baradwatchu/audit/reports/` per `status` e lo storico; su Windows usa `%LOCALAPPDATA%\baradwatchu\cache\audit\reports\`. `audit --json` stampa solo il JSON, ma crea comunque anche il PDF. Il report contiene versione e SHA-256 dell'agente, oltre allo stato e al percorso del PDF. Il JSON in cache conserva anche descrizione, riassunto e dettagli di esecuzione di ogni requisito, così il PDF usa i dati di quell'audit. Ogni audit genera automaticamente un PDF A4 nella cartella cache `baradwatchu/audit/`; se la generazione non riesce, l'audit termina normalmente e restituisce il motivo. `--log` scrive anche un `.log` in testo semplice con hash del client, tool, codici di uscita, diagnostica e percorso o errore PDF. I temi PDF sono file JSON in `~/.config/baradwatchu/themes/` su Linux e `%APPDATA%\baradwatchu\themes\` su Windows; `report-theme.json` memorizza l'ID selezionato. Il tema BaradWatchU integrato è sempre disponibile. Da Impostazioni o con `baradwatchu-agent report-theme use ID` si seleziona un tema; `baradwatchu-agent report-theme list` li elenca. La cartella cache si può cancellare: si perdono solo lo storico e l'ultimo risultato. Lo storico in `~/.local/state/baradwatchu/audits/` viene spostato lì automaticamente una volta. `list --json` e l'API della dashboard usano nomi di campo camelCase. `custom accept` e `custom remove` funzionano anche se la configurazione della cartella non è valida. I vecchi comandi `workstation`, `policy validate`, `audit --policy`, `audit --format` e `audit --local-config` sono stati rimossi; la CLI li rifiuta prima di leggere qualsiasi dato locale. Ogni audit completato (da CLI, dashboard o tray) aggiunge anche un evento a `~/.local/state/baradwatchu/events.jsonl` (si tengono gli ultimi 200); `events --json` è lo stato compatto che la tray interroga e `notifications` mostra o modifica le preferenze di notifica (`~/.config/baradwatchu/notifications.json`).

## Dashboard e notifiche

`baradwatchu-agent dashboard` serve la dashboard Angular su una porta effimera di `127.0.0.1` e la apre nel browser quando c'è una sessione desktop. Non avvia servizi e non ascolta sulla rete. Il loopback non è considerato un confine di sicurezza: ogni chiamata `/api/` richiede un token casuale di sessione (altrimenti `401`), le richieste che modificano dati devono anche provenire dall'origine della dashboard con corpo JSON, e l'intestazione `Host` deve corrispondere. Il browser riceve il token tramite un file di avvio privato (`$XDG_RUNTIME_DIR/baradwatchu/open-dashboard.html`, permessi 0600), quindi il token non compare mai sulla riga di comando di un processo; la scheda lo conserva in `sessionStorage` e lo toglie dalla barra degli indirizzi. Una seconda chiamata a `dashboard` (per esempio dalla tray) riusa l'istanza attiva registrata in `$XDG_RUNTIME_DIR/baradwatchu/dashboard.json` invece di avviarne un'altra. Usa le stesse impostazioni, lo stesso runner e lo stesso storico della CLI.

- **Stato postazione:** riepilogo dell'ultimo audit (i contatori filtrano l'elenco), filtri per esito, ricerca, requisiti ordinati per gravità dopo un audit, dettagli per requisito, impostazioni, parametri e dettagli tecnici/integrità compressi. Versione e SHA-256 dell'agente sono visibili insieme al percorso PDF; **Apri PDF** apre il report scaricato dalla cache locale. Gli audit storici si aprono dal pannello laterale senza modificare lo stato corrente. Il pannello mostra quanto spazio occupa lo storico; **✕** elimina un audit (report, log e PDF se presente) e **Svuota cronologia** li elimina tutti, compreso l'ultimo risultato, dopo una conferma. Da CLI: `history` elenca gli audit con la loro dimensione, `history delete STAMP` ne rimuove uno (STAMP = ora di completamento in Unix ms, come nell'elenco), `history clear --yes` li rimuove tutti. Vengono rimossi solo i file `<stamp>.json|.log|.pdf` nella cartella dello storico e nella sua sottocartella `reports/`; gli altri file restano.
- **Controlli personalizzati:** una sezione separata elenca i tuoi controlli con stato d'integrità e ultimo esito, e offre **Controlla ora**, **Accetta versione attuale**, **Carica nuovo file**, **Ripristina** l'integrato (per gli override) ed **Elimina**. Le cartelle non valide compaiono con il loro errore e si possono eliminare. **Nuovo controllo** apre il modulo di importazione: ID (viene proposto il primo `CUSTOM-NNN` libero), nome, descrizione, priorità, timeout, file, argomenti e, nelle opzioni avanzate, copia dei metadati o sostituzione di un integrato. Il file mantiene il suo nome nella nuova cartella. La sezione spiega anche la struttura delle cartelle e il formato dell'output.
- **Notifiche:** preferenze di notifica (notifiche desktop sì/no, informative sì/no), stato della tray, storico locale degli eventi e richieste di consenso. **Simula una richiesta** crea una richiesta di prova locale da 60 secondi; la dashboard non decide mai una richiesta. `#/history` apre la pagina di stato sullo storico degli audit.
- **Impostazioni:** avvio della tray all'accesso (lo stesso interruttore di **Avvia al login** nel menu della tray; l'agente esegue la tray installata accanto a sé con `autostart enable|disable|status --json`, argomenti fissi, senza shell, timeout di 10 secondi), tema PDF (percorso logo PNG/JPEG, testo, sfondo e accento; i colori dei badge restano fissi), se la tray è installata e attiva (Linux: PID vivo; Windows: il lock esclusivo della tray su `tray.lock`), versione, sistema operativo, cartella di installazione e cartelle dei dati locali (impostazioni, controlli personalizzati, eventi e consenso, storico degli audit, file di sessione), oltre all'identità del Client e ai Server trusted (vedi [Identità e Server trusted](#identità-e-server-trusted)). La disinstallazione non cancella mai queste cartelle. Si apre con `dashboard --open settings` o `#/impostazioni`.
- **Lingua:** Impostazioni offre `System default`, `Italiano` e `English`; la scelta per utente è salvata in `language.json` e condivisa da agente e tray. La scelta automatica rileva la lingua preferita dell'interfaccia macOS (`AppleLanguages`, con `AppleLocale` come ripiego), la lingua interfaccia Windows o le variabili locale POSIX (incluse le liste GNU `LANGUAGE`); se la lingua manca o non è supportata usa l'inglese (`en_EN`). I cataloghi JSON condivisi sono `crates/messages/locales/en_EN.json` e `it_IT.json`, incorporati negli eseguibili durante la compilazione. Se manca una traduzione viene mostrata la sua chiave come etichetta. I messaggi dell'interfaccia CLI, dashboard, tray e PDF usano questi cataloghi. Le evidenze dell'audit e l'output dei tool personalizzati restano invariati. La verifica runtime su Windows/macOS non è disponibile nell'attuale ambiente Linux.

Build di sviluppo:

```sh
cd web && npm ci && npm run build && cd ..
cargo run -p baradwatchu-agent -- dashboard
```

Le notifiche native sono inviate dalla tray (vedi sotto), anche quando nessun browser è aperto. Senza tray, `baradwatchu-agent audit --notify` chiede ancora a `notify-send` di mostrare il riepilogo dell'audit; con la tray attiva duplica la notifica della tray. Gli audit dalla dashboard non chiamano più `notify-send`.

Un `PASS` personalizzato è un'affermazione del tool stesso, non una prova di sicurezza indipendente. Il Server non ha ancora un catalogo degli audit né una registrazione autenticata, quindi non verifica questi hash.

## Tray

`baradwatchu-tray` è un piccolo processo separato per la sessione desktop dell'utente. Non esegue audit da solo: avvia l'agente installato accanto a sé con un insieme fisso di sottocomandi (`events --json`, `audit --json`, `dashboard --open …`, `consent accept|reject ID --via window`, e il processo di lunga durata `remote link --watch-stdin` per le [richieste di audit remote](#richieste-di-audit-remote)), senza shell e con timeout. L'agente funziona anche senza tray, e chiudere la tray non arresta l'agente né una dashboard aperta. Gira una sola tray per utente (file di lock `$XDG_RUNTIME_DIR/baradwatchu/tray.lock`); un secondo avvio segnala che è già attiva.

- **Menu:** riga di stato e ultimo audit, Apri dashboard, Esegui audit (disattivato durante l'esecuzione), Visualizza ultimo risultato, Storico audit, Richieste in sospeso, Notifiche recenti, Avvia al login, Informazioni, Chiudi tray.
- **Icona:** verde operativo, blu ardesia nessun audit ancora, ambra `FAIL`/`WARN`, rossa `ERROR` o blocco di integrità, blu richiesta in attesa di decisione, grigia agente non raggiungibile. Il tooltip riporta separatamente conteggi, blocchi di integrità e controlli personalizzati e precisa che l'esito dei controlli locali non è una certificazione di sicurezza.
- **Notifiche:** una per audit, classificata in base all'aspetto più grave (problema di integrità, errore di esecuzione, anomalie, completato). Ogni evento compare una sola volta; al massimo tre per interrogazione, le altre riassunte; un insieme di anomalie identico all'audit precedente conta come informativo. L'agente non raggiungibile viene notificato una volta, dopo due interrogazioni fallite (ogni 5 s), e il ripristino una volta. Preferenze: tutte le notifiche disattivate, oppure solo le informative; le richieste di consenso non si possono silenziare.
- **Richieste di consenso:** l'agente modella una richiesta del report della postazione con `requestId`, ID del server, nome e ID dell'account, dispositivo dichiarato, operazione (`AUDIT_REPORT`), scadenza e stato. Le richieste sono simulate in locale (`consent simulate`, pulsante della dashboard; non viene inviato nulla) oppure arrivano da un Server trusted autenticato con mutual TLS (origine `REMOTE_SERVER`, vedi [Richieste di audit remote](#richieste-di-audit-remote)); la richiesta remota indica il Server, il suo ID e il fingerprint della chiave. La tray apre una finestra dedicata (zenity, oppure kdialog in alternativa su Linux): **Accetta**, **Rifiuta**, **Decidi più tardi**. Accetta non è mai il pulsante predefinito. Solo un Accetta esplicito autorizza, e solo quella richiesta; rifiuto, chiusura, «decidi più tardi», timeout e una notifica soltanto mostrata non autorizzano nulla, e una richiesta scaduta non si può accettare. Si può decidere anche con `baradwatchu-agent consent accept|reject ID`.
- **Avvio al login:** `baradwatchu-tray autostart enable|disable|status` oppure la casella nel menu. Su Linux scrive `~/.config/autostart/baradwatchu-tray.desktop` (XDG, usato da KDE Plasma); su Windows usa la chiave per utente `HKCU\…\Run`; su macOS un LaunchAgent per utente limitato alla sessione Aqua. Nessun privilegio di amministratore; il servizio di sistema per le richieste remote è gestito dall'installer principale (vedi **Compilazione e installazione**).

Librerie: [`tray-icon`](https://github.com/tauri-apps/tray-icon) 0.26 (su Linux il backend `ksni` StatusNotifierItem via D-Bus, quindi non servono librerie GTK/AppIndicator), [`notify-rust`](https://github.com/hoodie/notify-rust) 4.18 (D-Bus freedesktop, toast di Windows, Centro notifiche di macOS) e, solo su Windows/macOS, `tao` 0.37 (ciclo di eventi) e `rfd` 0.18 (finestre di messaggio). Il framework Tauri completo e le WebView non sono usati; la dashboard resta nel browser.

**Stato delle piattaforme.** Linux (Arch, KDE Plasma 6 su Wayland) è compilato e verificato da cima a fondo. Il codice Windows e macOS supera il controllo dei tipi e Clippy (`cargo check`/`cargo clippy --target x86_64-pc-windows-msvc|x86_64-pc-windows-gnu|aarch64-apple-darwin|x86_64-apple-darwin`; per macOS la parte Objective-C di `mac-notification-sys` richiede l'SDK Apple e non è stata compilata). Su Windows 11 girano l'agente, i suoi controlli, la dashboard e la tray (vedi [Windows](#windows-in-sviluppo)); la tray è stata avviata, ha interrogato l'agente, ha rifiutato una seconda istanza e si è chiusa su richiesta, ma menu, notifiche e finestra di consenso non sono ancora stati provati lì. macOS non è mai stato eseguito e **non è supportato**. Su Windows la tray è un programma con sottosistema grafico (nessuna finestra di console); --version, --help e utostart scrivono sul terminale che l'ha avviata o sull'output reindirizzato (in PowerShell usa una pipe, per esempio `baradwatchu-tray --version | Out-String`, così PowerShell ne attende la fine). Si chiude in modo pulito quando riceve un WM_CLOSE sulla sua finestra invisibile «BaradWatchU Tray», ed è così che install.ps1 le chiede di chiudersi. Su Windows/macOS la finestra di consenso non si chiude da sola alla scadenza (un Accetta tardivo viene rifiutato dall'agente).

## Identità e Server trusted

Facoltativa e locale. Queste chiavi autenticano Client e Server nelle [richieste di audit remote](#richieste-di-audit-remote) (Milestone 2, disattivate per impostazione predefinita). La fiducia non nasce dalla rete: le chiavi pubbliche si scambiano prima, attraverso canali esterni verificati, e si importano localmente.

- **Perché generare le chiavi.** Una coppia di chiavi Ed25519 permetterà a un BaradWatchU Server di riconoscere questa postazione e di inviarle una richiesta di audit. Anche un Server trusted può solo *presentare* una richiesta: ogni audit remoto dovrà essere accettato dall'utente tramite la notifica/finestra di consenso già esistente. Un Server sconosciuto o revocato non può chiedere nulla. Senza chiavi il Client funziona normalmente (audit locali, dashboard, storico, PDF).
- **Solo su richiesta.** Le chiavi si generano solo con `identity generate` o **Genera identità** in Impostazioni, dopo il messaggio di conferma obbligatorio. Installazione, avvio, audit e aggiornamenti non le creano mai. File mancanti o danneggiati non vengono mai rigenerati: lo stato diventa *danneggiata* e il reset completo è il recupero esplicito. Un secondo `generate` viene rifiutato e rimanda al reset.
- **Chiave pubblica e privata.** La chiave pubblica (base64 standard di 32 byte), il suo fingerprint e il Device ID si possono condividere. La chiave privata resta in `private.key` su questo dispositivo (file `0600` in cartelle `0700` su Linux/macOS, controllati a ogni uso; su Windows ACL protetta per il solo utente e SYSTEM, impostata alla creazione) e non viene mai mostrata, copiata, esportata, restituita dall'API della dashboard né scritta in log, audit, PDF o notifiche. La firma viene rifiutata se i file delle chiavi sono accessibili ad altri utenti.
- **Formati.** Fingerprint = `SHA256:` + 64 cifre esadecimali minuscole dello SHA-256 dei 32 byte grezzi della chiave pubblica. Device ID = `BWU-XXXX-XXXX-XXXX-XXXX` (primi 64 bit dello SHA-256 di `baradwatchu.device-id.v1\0` + chiave pubblica); ID Server = `SRV-…`, derivato allo stesso modo da `baradwatchu.server-id.v1\0`. Esportazione e importazione usano il JSON versionato `baradwatchu.public-identity.v1`: `{schemaVersion, role: "client"|"server", id?, name?, algorithm: "Ed25519", publicKey, fingerprint?, createdAtUnixMs?}` (campi sconosciuti rifiutati); `id` o `fingerprint` dichiarati vengono ricalcolati dalla chiave e devono coincidere.
- **Scambiare la chiave pubblica.** `identity export [--output FILE]` o **Esporta identità pubblica (.json)** producono quel file; **Copia chiave pubblica** copia la chiave completa anche quando è nascosta dietro l'icona a occhio (nascosta per impostazione predefinita). Consegnala di persona o tramite un canale sicuro e conferma il fingerprint con il gestore del Server attraverso un canale indipendente (telefono, di persona).
- **Importare un Server trusted.** Solo da un file locale ricevuto fuori banda (USB, CD, messaggio firmato PGP…): `trust import FILE` o **Importa chiave Server…** in Impostazioni. Il Client mostra nome, ID Server e fingerprint e importa solo dopo una conferma esplicita (CLI: digita «sì», oppure passa `--fingerprint` con il valore verificato, obbligatorio senza terminale; dashboard: la casella di verifica, e l'agent ricontrolla che il fingerprint confermato corrisponda al file). Rifiutati: file malformati, identità di Client (`role: "client"`), chiavi deboli, la chiave dello stesso Client, chiavi già presenti, un nome già usato da un Server trusted, chiavi revocate. Il Client non accetta mai una chiave presentata da un dispositivo remoto: niente trust on first use, niente pairing via rete.
- **Gestire i Server.** `trust list|show|revoke` e il pannello **Server trusted** (dettagli, **Revoca**). La revoca conserva la voce (stato `REVOKED`, data di revoca), così la chiave non può essere reimportata in silenzio.
- **Rimuovi tutti i Server trusted** (`trust clear`) dimentica tutti i Server, comprese le revoche registrate, e conserva chiavi, Device ID e fingerprint del Client. Non è un reset.
- **Reset completo** (`identity reset`, **Reset completo…**): solo se sospetti che la chiave sia compromessa o stai inizializzando il PC per un nuovo Server. Sostituisce la coppia di chiavi (nuovo Device ID e fingerprint), svuota il trust store e fa scadere le richieste di consenso in attesa; dopo, la nuova chiave pubblica va scambiata di nuovo fuori banda con ogni Server. Conferma: digita `RESET` (CLI e dashboard); senza terminale serve `--yes`.
- **Sospetta compromissione.** Esegui il reset completo, consegna la nuova chiave pubblica ai Server che usi ancora e chiedi ai loro gestori di revocare dalla loro parte la vecchia chiave/Device ID; finché non lo fanno, una chiave privata rubata può ancora impersonare questa postazione verso di loro.
- **Coerenza e recupero.** Tutto si trova in `$XDG_STATE_HOME/baradwatchu/identity/` (Windows `%LOCALAPPDATA%\baradwatchu\state\identity\`, non roaming). Sotto un lock esclusivo, ogni modifica scrive file nuovi (`key-…/`, `trust-….json`), li scarica su disco e poi sostituisce in modo atomico `state.json`, l'unico punto di commit; i file non più referenziati vengono rimossi dalla stessa modifica o dalla successiva. Un'interruzione lascia lo stato precedente o quello nuovo, mai una chiave nuova con il vecchio trust store; uno `state.json` mancante o corrotto viene segnalato come danneggiato e nulla viene cancellato o adottato fino al reset completo. Generazioni concorrenti producono una sola identità.
- **Limiti della protezione locale.** I permessi dei file fermano gli altri utenti, non i processi dello stesso utente (possono leggere la chiave privata come qualsiasi suo file), gli amministratori/root, i backup o un endpoint compromesso. Le vecchie chiavi private vengono sovrascritte prima della cancellazione al meglio delle possibilità, ma SSD, filesystem copy-on-write, snapshot e backup possono conservarne i byte. Non si usano ancora TPM, Secure Enclave o keystore del sistema operativo. Su Windows l'ACL è impostata alla creazione e non riverificata (indicata come «non riverificata»).
- **API della dashboard** (stessi controlli di token, `Host`, `Origin` e JSON del resto del bridge): `GET /api/identity`; `POST /api/identity/generate|reset`, `/api/trust/clear`, `/api/trust/revoke/SERVER-ID` con corpo esattamente `{"confirm":true}`; `POST /api/trust/preview` `{content}` e `/api/trust/import` `{content, confirmFingerprint}`. Nessuna risposta contiene materiale della chiave privata.
- **Per le prossime milestone** (`crates/agent/src/identity.rs`): `public_identity`, `sign`, `verify_signature` (Ed25519 rigoroso), `trusted_server_for_key` (confronta la chiave completa, mai nome, indirizzo o ID dichiarato) e `check_remote_request`, il cui esito migliore è `RequiresLocalConsent`: nessun esito autorizza l'esecuzione di un audit.
- **Codici di uscita** di `identity`/`trust`: 0 eseguito, 1 annullato dall'utente (nessuna modifica), 2 errore d'uso o fallimento.

## Richieste di audit remote

Milestone 2. Un BaradWatchU Server trusted può **chiedere** un audit di questa postazione; l'audit parte solo dopo che l'utente accetta nella finestra di consenso della tray. Non esiste accettazione automatica, neppure per i Server trusted, e un Server non può mai eseguire comandi né modificare chiavi o trust store. Disattivato per impostazione predefinita su tre livelli: un amministratore installa il servizio di sistema, un amministratore configura l'indirizzo del listener, e ogni utente abilita le richieste remote dopo aver generato la propria identità. Protocollo ed endpoint: [docs/remote-protocol.md](docs/remote-protocol.md) (in inglese).

- **Componenti.** `baradwatchu-agent service run` è il servizio di sistema sempre attivo (unit systemd `baradwatchu-agent.service`, LaunchDaemon `io.baradwatchu.agent`, servizio Windows `BaradWatchU`; riavviato dal sistema operativo in caso di errore). Gestisce il listener mutual TLS, risponde `UNAVAILABLE`/`BUSY`, conserva i record delle richieste e non esegue mai audit. `baradwatchu-agent remote link` è l'agent per utente: lo avvia (e lo riavvia) la tray, mostra la richiesta di consenso ed esegue il solito motore di audit come utente, e si ferma con la tray. Stesso eseguibile, nessun broker, nessun nuovo framework.
- **Un'identità per utente.** Il servizio non ha chiavi proprie e non ne crea. `remote enable` registra presso il servizio la cartella dell'identità dell'utente stesso: il sistema operativo dice al servizio quale account sta chiamando (credenziali del socket, impersonificazione della named pipe), e ogni file di chiave deve appartenere a quell'account ed essere accessibile solo a lui. Quando un Server si collega con SNI = Device ID, il servizio risponde con la chiave Ed25519 di quell'utente, letta dalla sua cartella (root/LocalSystem possono leggerla; la registrazione decide quale, e il servizio non sceglie mai un utente da solo). Più utenti dello stesso PC possono registrarsi, ognuno con il proprio Device ID e trust store. Dopo `identity reset` esegui di nuovo `remote enable`; `remote disable` rimuove la registrazione.
- **Trasporto.** TLS 1.3 con chiavi pubbliche Ed25519 grezze (RFC 7250; rustls con backend ring) da entrambi i lati. Le chiavi che dimostrano il possesso durante l'handshake sono quelle della Milestone 1 e vengono confrontate con il trust store dell'utente (solo `TRUSTED`). Chiavi sconosciute, revocate o non corrispondenti e Device ID non registrati fanno fallire l'handshake prima di qualsiasi scambio di dati. Niente certificati X.509 né CA, nessuna autenticazione per indirizzo IP, hostname o contenuto della richiesta, nessuna ripresa di sessione.
- **Flusso.** `POST /v1/audit-requests` apre la finestra di consenso (120 secondi da quando compare). Solo dopo **Accetta** l'audit parte; il Server interroga `GET /v1/audit-requests/{id}` e scarica `…/result`. Solo il Server richiedente vede la richiesta e il suo risultato. Lo stesso `requestId` è la stessa richiesta e non viene mai eseguito due volte; le richieste emesse a più di 5 minuti dall'orologio del Client vengono rifiutate.
- **Disponibilità.** Nessun utente collegato, tray non in esecuzione o sessione che non risponde: `UNAVAILABLE`. Schermo bloccato: la richiesta attende; se l'utente sblocca e accetta entro 120 secondi l'audit parte, altrimenti è `EXPIRED` (il blocco schermo non viene mai aggirato). Una richiesta in attesa di consenso o qualsiasi audit in corso (CLI, tray, dashboard o remoto): `BUSY` immediato, nessuna coda. Un audit locale avviato nel frattempo viene rifiutato con un messaggio.
- **Revoca e reset.** `trust revoke`, `trust clear` e `identity reset` ritirano subito le richieste remote in attesa; la connessione successiva di quel Server fallisce all'handshake e nessun risultato gli viene consegnato.
- **Stato.** `remote status [--json]` mostra separatamente: servizio installato, servizio in esecuzione, listener remoto (disabilitato, in ascolto, in errore), identità disponibile, Server trusted, richieste remote abilitate per questo utente, sessione utente collegata, tray in esecuzione.
- **Installazione e configurazione.**
  1. Usa l'**installazione di sistema** del Client: il servizio ne fa parte (vedi **Modalità di installazione** più sotto). Linux: `./install.sh` (predefinito `/usr/local`). Windows: il setup per tutti gli utenti (il suo predefinito). macOS non ha ancora un installer del Client: lì esegui a mano `sudo packaging/service/install-service.sh [--agent=PERCORSO]`. Un'installazione per utente non ha il servizio e non può ricevere richieste remote.
  2. Verifica: `systemctl status baradwatchu-agent.service` (Windows: `Get-Service BaradWatchU`), oppure `baradwatchu-agent remote status` come utente.
  3. Configura il listener in `service.json` nella cartella del servizio (`/var/lib/baradwatchu`; macOS `/Library/Application Support/BaradWatchU/service`; Windows `%ProgramData%\BaradWatchU\service`): `{"schemaVersion":"baradwatchu.service-config.v1","remote":{"listen":"INDIRIZZO:PORTA"}}`, poi riavvia il servizio. Scegli l'interfaccia (per esempio l'indirizzo della VPN). Le regole del firewall spettano all'operatore o all'IT.
  4. Ogni utente: `identity generate`, `trust import SERVER.json`, `remote enable`, con la tray in esecuzione.

  Gli installer non generano mai chiavi, non scrivono mai `service.json` (quindi il listener resta spento), non toccano il firewall, e l'avvio automatico della tray non cambia.
- **Stato delle piattaforme.** Linux: implementato e testato da cima a fondo con i veri eseguibili e un harness che fa la parte del Server (`crates/agent/tests/remote_service.rs`: accettazione, rifiuto, timeout di 120 secondi in tempo reale, accettazione tardiva, nessuna sessione, nessuna tray, `BUSY` contro audit remoti e locali, chiavi sconosciute/revocate/non corrispondenti, duplicati e replay, revoca e `trust clear` con consenso in attesa, reset, riavvio del servizio, disconnessione del Server, endpoint della dashboard assenti, nessuna chiave privata nelle risposte). Il servizio è stato eseguito come utente sviluppatore; la unit systemd supera `systemd-analyze verify` ma **non è ancora stata eseguita come root**. L'integrazione nell'installer (prima installazione, aggiornamento con stop e riavvio verificato, ripristino dopo un'installazione fallita, servizio che non parte, aggiornamento di un'installazione precedente al servizio, disinstallazione con dati conservati, servizio di un'altra installazione rifiutato senza modifiche, agent non di root rifiutato) è stata testata in un namespace isolato; la modalità per utente (senza sudo, senza servizio, installazione/reinstallazione/disinstallazione) come utente reale (namespace: `systemctl` simulato che esegue il vero `service run`); il vero systemd non è ancora stato pilotato. Windows (named pipe, servizio Windows, controllo del proprietario via ACL, il setup per tutti gli utenti con il suo servizio) e macOS (LaunchDaemon, `getpeereid`): codice scritto; il codice Rust è controllato solo con Clippy in cross-compilazione, lo script del setup e `install-service.ps1` non sono stati compilati né eseguiti. **Non eseguiti, non ancora supportati.**

## Build e installazione

L'installer da sorgente compila come utente normale e usa `sudo` solo per copiare i file in un prefix protetto:

```sh
./install.sh --missing-deps                        # controllo dipendenze in sola lettura
./install.sh --dry-run                             # mostra il piano
./install.sh                                       # compila e installa in /usr/local
./install.sh --build-only --build-dir=DIR          # compila e valida solo la cache
./install.sh --no-tray-autostart                   # prima installazione senza avvio della tray al login
./install.sh --without-tray                        # solo agente e dashboard
./install.sh --local                              # installazione per utente in ~/.local (senza servizio)
./install.sh -U                                    # disinstalla (servizio compreso; dati conservati)
```

Ogni esecuzione inizia con un riepilogo delle opzioni effettive. Il controllo delle dipendenze elenca:

- **[REQUIRED] strumenti di build** (Rust/Cargo ≥ 1.92 con la tray, ≥ 1.80 con `--without-tray`; strumenti C/C++, make, tar, glibc, Node.js 20 ≥ 20.11.1 selezionato tramite `web/.nvmrc` e nvm se disponibile, npm) e **[REQUIRED] strumenti di runtime** usati da agente e controlli (bash, python3, awk, sed, grep, coreutils). Se ne manca uno l'installer si ferma prima di compilare o modificare file e stampa il comando per installarlo.
- **[optional] strumenti di audit — solo Arch Linux** (`checkupdates`, `systemctl`, `ufw`/`firewalld`/`nftables`, `dnsmasq`, Cato/`wg`, `lsblk`, `findmnt`, `kreadconfig6`, `pgrep`, `chage`, `systemd-analyze`, `notify-send`, `xdg-open`), ciascuno con il controllo che lo usa. Se ne manca uno l'installazione non si blocca; il relativo controllo dà `WARN`. Per le alternative (un firewall, un client VPN) ne basta uno. Sulle altre distribuzioni la sezione viene saltata con una nota, perché i controlli integrati sono pensati per Arch.
- **[optional] tray:** `zenity` o `kdialog` per la finestra di consenso (senza, la tray chiede di decidere con la CLI). La tray richiede anche una sessione desktop con D-Bus e un host StatusNotifierItem (KDE Plasma; GNOME richiede l'estensione AppIndicator).

Con la tray (predefinito) l'installer aggiunge al manifest `bin/baradwatchu-tray` e la voce di menu `share/applications/baradwatchu-tray.desktop`. **Avvio al login:** una prima installazione (senza manifest) attiva l'avvio della tray al login per l'utente che lancia l'installer dopo aver installato i file (come quell'utente, mai come root); `--no-tray-autostart` lo evita. Una reinstallazione o un aggiornamento mantengono la scelta attuale dell'utente, che si cambia dal menu della tray (**Avvia al login**) o con `baradwatchu-tray autostart enable|disable`; `--tray-autostart` la attiva comunque. La disinstallazione rimuove la voce di avvio automatico di quell'utente se punta a questa installazione.

**Istanze in esecuzione:** prima di sostituire o rimuovere file, un `baradwatchu-agent` o `baradwatchu-tray` avviato dalla stessa installazione (riconosciuto dal percorso dell'eseguibile, mai dal nome; per esempio una dashboard aperta) riceve SIGTERM e ha fino a `BARADWATCHU_STOP_TIMEOUT` secondi (predefinito 10) per chiudersi. Non viene mai ucciso: se non si chiude, l'installer si ferma senza modificare nulla. Le istanze di altri utenti vengono solo segnalate. `--dry-run` mostra che cosa verrebbe chiuso.

**Modalità di installazione.** La modalità decide che cosa viene installato; installazione, aggiornamento e disinstallazione la rispettano sempre.

| Modalità | Quando | Contenuto |
|---|---|---|
| **Di sistema** (distribuzione standard) | un prefisso che richiede root (predefinito `/usr/local`); setup Windows per tutti gli utenti | il Client completo: agent, dashboard, tray e il **servizio di sistema** che serve le API remote mTLS |
| **Per utente** (locale) | `--local`, oppure un `--prefix` scrivibile senza root; su Windows `install.ps1` e il setup «solo per me» | agent, dashboard, tray, identità, trust store, audit locali e report, senza diritti di amministratore; **nessun servizio di sistema, nessuna comunicazione remota** |

Un'installazione per utente non è un'installazione guasta: serve per sviluppo, test e diagnostica, e tutto ciò che è locale funziona. Non esiste una variante per utente del servizio. Il riepilogo all'inizio di ogni esecuzione mostra le righe `mode` e `service`; `--dry-run` non modifica nulla.

**Servizio di sistema** (richieste di audit remote, Milestone 2). `install.sh` è l'unico punto d'ingresso: nel passaggio che già usa `sudo` richiama `packaging/service/install-service.sh`, suo componente interno (lo script si può ancora eseguire a mano, ed è la strada su macOS). Compilazione, controllo delle dipendenze e avvio automatico della tray restano senza privilegi.

- **Sempre nell'installazione di sistema.** L'installazione e ogni aggiornamento installano o aggiornano la unit systemd `baradwatchu-agent.service` (root, attiva all'avvio, riavviata in caso di errore); anche un'installazione esistente fatta prima del servizio lo riceve al prossimo aggiornamento. Non ci sono opzioni per escluderlo: se viene *usato* lo decidono `service.json` (listener) e ogni utente (`remote enable`). Un solo servizio per macchina: se appartiene a un'altra installazione, l'installer si ferma prima di modificare qualsiasi cosa e spiega come rimuoverlo. L'installazione di sistema richiede systemd; senza, usa `--local`.
- **Mai un eseguibile vecchio.** Prima di modificare qualsiasi file, il servizio di questa installazione viene fermato (poi vengono chiuse le solite istanze in esecuzione); quando i file sono al loro posto viene riavviato e l'installer verifica che il processo in esecuzione sia esattamente il nuovo `bin/baradwatchu-agent` (non un file sostituito). Se l'installazione fallisce prima di quel punto (per esempio una dashboard che non si chiude), il servizio viene riavviato sui file presenti. Se è il servizio a non partire, l'installer lo ferma, segnala che i file sono installati e stampa il comando per riprovare; termina con errore.
- **Disinstallazione** (`-U`): ferma e rimuove il servizio di questa installazione prima di rimuovere i file.
- **Conservati, sempre:** identità, trust store, impostazioni, controlli personalizzati, eventi e storico di ogni utente, e la cartella del servizio `/var/lib/baradwatchu` (registrazioni, record delle richieste, `service.json`). Rimuovi quella cartella a mano solo per dimenticare le registrazioni: `sudo rm -r /var/lib/baradwatchu`. L'installer non genera mai chiavi, non scrive mai `service.json` (il listener resta spento) e non tocca il firewall.

L'installer mantiene cache di build, reinstallazione e disinstallazione basate sul manifest; impostazioni utente, controlli personalizzati e storico non vengono mai toccati. Non crea pacchetti del package manager. `./install.sh --help` elenca tutte le opzioni.

### Windows: install.ps1 e setup.exe

`install.ps1` è l'equivalente Windows di `install.sh`. Installa **per utente, senza diritti di amministratore** e senza servizi. Windows blocca per impostazione predefinita gli script non firmati, quindi va avviato tramite Windows PowerShell con un bypass valido solo per quel processo:

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1 -MissingDeps   # controllo dipendenze in sola lettura
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1 -DryRun        # mostra il piano
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1                # compila e installa
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1 -NoTrayAutostart # prima installazione senza avvio all'accesso
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1 -WithoutTray   # solo agente e dashboard
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1 -Uninstall     # disinstalla
powershell -NoProfile -ExecutionPolicy Bypass -File .\install.ps1 -Package       # genera invece setup.exe
```

- **Dipendenze:** [REQUIRED] Rust ≥ 1.92 con toolchain MSVC (≥ 1.80 con `-WithoutTray`), Visual Studio Build Tools con il carico di lavoro C++, Node.js 20 ≥ 20.11.1 e npm; a runtime Windows PowerShell 5.1. [optional] Inno Setup 6 per `-Package` e le fonti dei controlli (modalità FullLanguage di PowerShell, cmdlet di Defender e NetSecurity, Cato Client). Per ogni elemento mancante viene stampato il comando `winget`.
- **Build:** come su Linux, una cache validata fuori dal sorgente (predefinita `%LOCALAPPDATA%\baradwatchu\build\baradwatchu-agent-VERSIONE`, `-BuildDir`, `-BuildOnly`, `-NoBuild`), con la build Angular in una copia privata di `web`, un'impronta dei sorgenti (modifiche durante la build o dopo la build in cache vengono rifiutate), il controllo della versione di entrambi gli eseguibili e la stessa verifica di integrità dei controlli integrati Windows rispetto a `builtin-tools.sha256`.
- **Installazione:** predefinita `%LOCALAPPDATA%\Programs\BaradWatchU` (`-Prefix`), struttura `bin\*.exe` + `share\baradwatchu-client\{catalog,web}`, manifest `share\baradwatchu-source\baradwatchu-agent.manifest` con lo SHA-256 di ogni file. File non gestiti o modificati localmente non vengono mai sovrascritti né rimossi; collegamenti simbolici e junction nel percorso sono rifiutati. Le voci **BaradWatchU Dashboard** e **BaradWatchU Tray** vengono create nel menu Start dell'utente e registrate nel manifest. L'avvio al login segue la stessa regola di Linux: attivato alla prima installazione (`HKCU\…\Run`, per evitarlo `-NoTrayAutostart`), lasciato come l'ha impostato l'utente a ogni reinstallazione (`-TrayAutostart` lo attiva comunque). La disinstallazione rimuove anche la voce `HKCU\…\Run` della tray se punta a questa installazione e le cartelle rimaste vuote. La cartella del menu Start e la voce `Run` sono condivise da tutte le installazioni BaradWatchU dell'utente (un altro `-Prefix` o il setup): le voci che puntano a un'altra installazione non vengono mai sovrascritte né rimosse, e l'avvio al login predefinito non si prende la voce `Run` di un'altra installazione (`-TrayAutostart` sì).
- **Istanze in esecuzione:** i programmi avviati dalla stessa installazione (riconosciuti dal percorso dell'eseguibile) vengono invitati a chiudersi prima di modificare i file: un helper di breve durata invia una richiesta di chiusura (WM_CLOSE) alla finestra della tray e un Ctrl+C sulla console di agente e dashboard (mai sulla console dell'installer). Hanno fino a `BARADWATCHU_STOP_TIMEOUT` secondi (predefinito 10) e non vengono mai terminati a forza: se uno resta attivo l'installer si ferma senza modificare nulla. Una dashboard avviata dal tuo terminale condivide quella console, quindi anche gli altri programmi collegati a essa ricevono lo stesso Ctrl+C.
- **Setup (`-Package`):** usa la stessa build validata e compila `packaging\windows\baradwatchu-client.iss` con Inno Setup 6 in `BaradWatchU-Client-VERSIONE-setup.exe` (predefinito `BUILDDIR\dist`, `-OutputDir`), stampandone lo SHA-256. Il setup installa per tutti gli utenti (predefinito) o solo per l'utente corrente (vedi **Modalità di installazione** più sotto), in italiano o inglese, con voci nel menu Start, un'attività «Avvia la tray all'accesso» (selezionata per impostazione predefinita e proposta solo alla prima installazione, così un aggiornamento mantiene la scelta dell'utente; per escluderla in modalità silenziosa `/MERGETASKS="!trayautostart"`; non viene proposta se la voce `Run` appartiene a un'altra installazione, e la disinstallazione la rimuove solo se avvia la tray di questa installazione) e il programma di disinstallazione in **Impostazioni › App**; gli aggiornamenti sostituiscono la stessa installazione. Setup e disinstallazione si rifiutano di procedere mentre un programma BaradWatchU di quella cartella è in esecuzione (codice di uscita 7 / 1, nulla modificato) e non lo terminano mai: chiudi prima dashboard e tray. Supporta le opzioni silenziose standard (`/VERYSILENT /SUPPRESSMSGBOXES`, `/DIR=`). `install.ps1` rifiuta una cartella gestita dal setup: usa un solo metodo per cartella. **Modalità di installazione:** il setup chiede **tutti gli utenti** (predefinito: l'installazione di sistema, amministratore, Program Files, in modalità silenziosa `/ALLUSERS`) oppure **solo per me** (installazione per utente, senza diritti di amministratore, `%LOCALAPPDATA%\Programs\BaradWatchU`, in modalità silenziosa `/CURRENTUSER`, senza servizio); un aggiornamento mantiene la modalità dell'installazione esistente, quindi le installazioni per utente già presenti restano per utente. L'installazione per tutti gli utenti installa o aggiorna sempre il servizio Windows `BaradWatchU` (LocalSystem, avvio automatico, riavvio in caso di errore) tramite `install-service.ps1`, installato in `share\baradwatchu-client\service`; se il servizio appartiene a un'altra installazione, il setup si ferma prima di modificare i file. Il setup ferma quel servizio prima di sostituire i file e lo riavvia sul nuovo eseguibile, verificando il processo in esecuzione; un setup rifiutato o annullato lo riavvia; se non riesce a partire, il setup lo segnala e lo lascia fermo. La disinstallazione lo rimuove prima di cancellare i file e conserva `%ProgramData%\BaradWatchU\service` e i dati di ogni utente. In modalità tutti gli utenti la voce di avvio automatico della tray viene scritta per l'utente che ha avviato il setup. L'`install.ps1` per utente non installa mai un servizio. Il setup **non è firmato**: SmartScreen mostra l'avviso di editore sconosciuto finché l'organizzazione non lo firma (per esempio con `signtool`), passaggio che qui non è automatizzato.

## Verifiche di sviluppo

```sh
cargo fmt --all -- --check
cargo test --workspace --locked
cargo clippy --workspace --all-targets --locked -- -D warnings
cd web && npm test && npm run build
```

Il controllo incrociato per Windows/macOS (`cargo clippy --target …`) richiede un compilatore C per il target a causa di `ring` (TLS): per esempio `clang-cl` con gli header del Windows SDK, oppure clang con l'SDK Apple.

Su Windows gli stessi comandi funzionano da una shell con la toolchain MSVC (Visual Studio Build Tools, carico di lavoro C++) e Node.js 20; per installare usa `install.ps1` (vedi sopra). I tool di prova sono script shell su Unix e script PowerShell su Windows; i test del runner basati solo su shell e le suite degli script integrati girano solo su Unix. I test puntano ogni directory XDG a cartelle temporanee private e serializzano le modifiche all'ambiente, quindi girano in parallelo e non toccano mai configurazione o storico dello sviluppatore. Gli script dei controlli integrati sono testati con file di fixture e comandi stub (`tests/workstation_criteria.rs`, `tests/req003_firewall.rs`, `tests/req004_005_methods.rs`). La logica della tray (stato dell'icona, politica delle notifiche, contratto dello snapshot) è testata senza GUI in `crates/tray/src/model.rs`.

## Limiti attuali

L'architettura legacy (valutazione delle policy, collector nativi Fedora/Arch, adapter, registro workstation, `policies/`, il vecchio `scripts/`, `configs/`) è stata rimossa il 2026-11-07; il sorgente contiene solo catalogo a cartelle, runner, CLI e dashboard. Alcuni controlli sono volutamente prudenti e restituiscono `WARN`; la validazione su host reali diversi dalla postazione Arch dello sviluppatore è ancora da fare. Non ci sono scheduler degli audit, policy remote, download dinamico dei tool, implementazioni di audit per macOS o remediation automatica. Su Windows ci sono un installer per utente e un setup non firmato (per tutti gli utenti con il servizio, oppure per utente), ma ancora nessuna firma del codice, e il servizio Windows non è mai stato eseguito; i suoi controlli girano senza diritti di amministratore, quindi dettagli di BitLocker, interrogazioni complete di Secure Boot/TPM e dati di `secedit` restano fuori portata, e la scheda Cato che segnala la connessione non è stata verificata su un dispositivo connesso. Le decisioni di consenso sono legate all'utente locale: qualsiasi processo dello stesso utente può chiamare `consent accept`, così come può leggere i file di quell'utente. I provider esistono solo per i requisiti integrati (per ora REQ-002): i provider personalizzati non sono implementati, il provider Bitdefender GravityZone non è stato validato su un endpoint gestito e gli script dei provider Windows non sono ancora stati eseguiti. Gli hash dell'installazione vengono riportati ma nessun Server li verifica ancora. La chiave privata è protetta solo dai permessi dei file del sistema operativo (niente TPM né keystore del sistema), e l'ACL su Windows e la build macOS non sono state provate in esecuzione. Richieste remote: il servizio di sistema legge la chiave privata di ogni utente registrato dalla sua cartella, quindi una home cifrata e non sbloccata (systemd-homed, FileVault, eCryptfs) o una home di rete con root squash rende irraggiungibile quell'utente (l'handshake fallisce, quindi il Server non riceve risposta invece di `UNAVAILABLE`); le richieste remote dipendono dalla tray (finestra di consenso); le richieste di consenso compaiono entro l'interrogazione della tray ogni 5 secondi; i risultati degli audit restano nella memoria del servizio per un'ora e si perdono al riavvio; un audit già in corso non viene annullato se la sessione scompare (il risultato resta locale); non c'è ancora un pannello della dashboard per le richieste remote (solo CLI `remote …`).

## Metadati richiedente Server MVP

Le richieste di audit remoto del Server MVP includono il nome dell'operatore Google e il
nome del Server. Il consenso mostra ancora identità e fingerprint del Server trusted
locale; il nome dell'operatore è descrittivo e non autorizza l'esecuzione.
I nuovi audit JSON, cronologia, dashboard locale e PDF distinguono `LOCAL` e `REMOTE`,
con nome del richiedente e riferimento al Server per gli audit remoti. I report storici
privi di attribuzione restano leggibili senza inventare un'origine.

L’intestazione PDF indica `CLIENT · REMOTE AUDIT` per i risultati remoti, `CLIENT · LOCAL AUDIT` per quelli locali e `CLIENT · ORIGIN UNKNOWN` per i report storici senza origine.

Aggiornare sia il servizio Client sia l'agente utente prima di collegare il Server MVP:
i vecchi lettori strict del protocollo v1 rifiutano il campo opzionale `requester`; quelli
aggiornati accettano ancora richieste precedenti senza metadati. Il consenso rimane di
120 secondi; i risultati remoti completati restano nella memoria del servizio per un'ora,
indipendentemente dalla cronologia locale. Vedere [il protocollo](docs/remote-protocol.md)
per campi aggiuntivi e compatibilità.
